# 方案取舍

本页记录模板自身的已采纳决策与理由。源工程（STS2-Navia）的历史取舍见其仓库的技术历史。

## 参数化优先于纯 sed 改名

普查发现 mod id 在脚本／工作流／工具里被字面重打约 90 次，而清单本就是声明的唯一事实源。模板让 `dev-env.sh` 从唯一根 json 导出 `MOD_ID`／`MOD_SHORT`／`MOD_LOC_PREFIX`，机械热点全部引用变量——init 的 sed 面收敛到「清单 + csproj + src 目录 + C# 命名空间 / Base 类名」。参数化在模板内即可回归验证（双目标编译 + 全审计 + 打包）。

## 示例内容用前缀式命名

示例类命名 `CharlotteStrike` 形态（前缀），而非源工程的 `StrikeNavia` 形态（后缀）：单一 `\bTemplate` 词边界规则即可全量改名，后缀式需要逐类显式令牌。`STS2-Charlotte-art`／`STS2-Charlotte.Loader` 等长令牌先于短令牌消解，`_` 不是词边界——令牌序是负载-bearing 的，调整顺序前先实测。

## 世界线不入骨架代码

纪元肖像是全局域 PNG，而仓库边界规则禁止跟踪一切媒体——骨架无法自证该模块。取舍：机制知识全部保留在可选模块文档（worldline.md），代码接线参照源工程。角色解锁属性随删。

## Loader 拷贝而非共享库

变体 Loader 以源码拷贝形式进每个衍生仓。理由：两个 Mod 规模下共享库增加依赖与版本协调成本；Loader 是最怕游戏版本更新的资产，拷贝让各 Mod 可独立热修。**触发线**：第三个 Mod 出现，或下一次游戏版本破坏加载链——届时抽为组织共享库（记录于[路线图](../roadmap.md)）。

## 私有侧走跟踪 templates/ 目录

`local_dev/` 整体忽略是仓库边界铁律，但纯私有侧文件到不了模板消费者。取舍：公开仓带 `templates/` 目录存放无密钥的脚手架（publish.sh 骨架、README 衍生视角等），init 时拷入 `local_dev/` 并预填配置，随后从衍生树删除。

## 身份三查入审计

audit-repository 增加「根目录恰一个 json 清单 + 文件名与 id 一致 + `src/<id>/` 存在」三项结构检查：参数化体系完全建立在「清单可被唯一发现且自洽」之上，破坏即大声失败。

## 模板仓不打 git tag

tag 会触发 Release 工作流,而模板仓没有发行物、也不持有构建凭据——首次 v1 tag 即触发了注定失败的 Release 构建(已删)。模板版本以 CHANGELOG 与 `.template-origin` 的标签字段承载,衍生仓按该字段对齐回流。
